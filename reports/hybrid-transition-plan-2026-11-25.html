Blookd API — поэтапный переход к гибридной архитектуре

План для проектного менеджера · 25 ноября 2026 · Код dev@75beb25f

Главная цель: получить преимущества отдельных сервисов без заметного изменения для пользователей. Мы не «разрезаем» систему одним релизом. Сначала закрываем риски, затем переносим по одной небольшой функции, сравниваем результаты и оставляем возможность немедленного возврата в монолит.

Русский · English · Оценка готовности · Сравнение с 08.11

1. Как будем двигаться

Безопасность→Измерения→Пилот→Отчёты→Уведомления→Web BFF→Решение по Core

Что означает «гибрид»

Основные операции — записи, платежи, отмены, профили и вход — остаются в модульном монолите. Отдельные процессы появляются только там, где есть понятная выгода: тяжёлые отчёты, фоновые уведомления и web-трафик.

Почему не полный распил

Booking, Payments и Cancellation связаны общими данными и транзакциями. Их преждевременное разделение создаст сетевые задержки и риск двойных списаний, но не даст независимых сервисов.

Правила для каждого этапа

  • Сначала прежнее поведение: public URL, поля ответов, статусы и ошибки не меняются.
  • Local по умолчанию: монолит работает без нового сервиса.
  • Shadow перед переключением: пользователь получает ответ монолита, а новый путь только сравнивает результат.
  • Маленькие cohorts: одна сущность или небольшой процент трафика, затем постепенное расширение.
  • Обратимые изменения БД: сначала добавляем новое, удаляем старое только после стабилизации.
  • Rollback без нового кода: конфигурация или nginx возвращает local; один процесс за цикл стабилизации.

0. Security gate Закрыть известные денежные и security-риски Никаких изменений, кроме запрета опасных legacy-операций Критические пути закрыты и проверены тестами
1. Production readiness Владельцы, метрики, секреты, backup, alerts Никаких изменений Есть baseline и проверенный rollback
2. Provider-share rehearsal Проверить сам механизм выноса на read-only операции Те же профили и ссылки Shadow без расхождений и успешный возврат local
3. Reporting worker Вынести тяжёлые PDF/XLSX/email из API-процесса Те же отчёты, суммы и сроки ответа Отчёты совпадают; ресурсы API стабильны
4. Notification worker Безопасно выполнять push/SMS/email вне API Те же уведомления, без потерь и дублей Outbox полный, DLQ/alerts работают, retry без повторного эффекта
5. Web BFF Отделить web-трафик от мобильного/core Те же URL, вход, сессии и каталог Каждая route group переключена и откачена без контрактных изменений

3. Подробности и критерии завершения

Этап 0. Закрыть обязательные security-риски

Работы: отключить или защитить createtransfers; подтвердить production PAN/CVV flag и purge; включить поэтапную миграцию паролей Argon2id; закрыть достижимые SQL-инъекции; заменить public paths по сегментам на точный реестр; отозвать APNs и старые секреты.

Зачем: распределённая система увеличивает число точек доступа. Переносить открытые деньги, пароли и auth-обходы нельзя.

Готово: опасный transfer невозможен, production CVV=0 по подтверждению, live SQL/auth тесты зелёные, секреты отозваны, нет критических/high dependency advisories.

Этап 1. Подтвердить эксплуатационную готовность

Работы: назначить primary/backup owner; применить sidecar migration; настроить private network, service credential, DB least privilege, strict env; включить branch protection; проверить backup/restore; настроить dashboard и реальные PagerDuty/Slack routes.

Измерения: local DTO/404, RPS, p95/p99, error rate, DB pool, живые v1 routes, отчёт по тяжёлым SQL. Снимок production схемы обновляется по runbook.

Готово: владелец принял runbook, alerts проверены искусственным сбоем, baseline записан, restore и rollback выполнены на target.

Этап 2. Provider-share — репетиция механизма

Почему этот шов: только чтение небольшого DTO, нет платежей, auth-решений или внешних эффектов. Обе стороны читают одну MySQL-схему, поэтому откат не требует обратной синхронизации.

  1. Запустить отдельный image в local, проверить health/readiness.
  2. Включить shadow на одном slug, затем на небольшой доле.
  3. Сравнить DTO, 404, latency, errors и side effects.
  4. Включить remote для одного slug, затем постепенно увеличить cohort.
  5. Несколько раз вернуть local конфигурацией и проверить отсутствие remote-зависимости.

Готово: ноль необъяснённых mismatches, remote errors ниже бюджета, rollback задокументирован. Затем 14 дней 100% remote. Contract и удаление local только после этого.

Этап 3. Reporting worker — первый реальный workload

Почему: PDF/XLSX потребляют CPU и память и могут мешать API. Это уже выделенная задача с read-only доступом к данным.

Работы: internal API с service credential; read-only primary DB user; сравнение PDF/XLSX и финансовых сумм; sandbox email; ограничение параллелизма и timeout; REPORT_EXECUTION=local|remote. Async jobs и read replica — отдельное позднее решение.

Готово: побайтовая или структурная parity, прежние 200/400/403/429/500, стабильная память Core, неделя без регрессий, rollback local.

Этап 4. Notification worker

Почему не раньше: уведомления создают внешние эффекты. Потеря или повтор события уже заметна пользователю.

Работы: каждый producer пишет business row + outbox в одной транзакции; один notification writer; idempotent consumer; retry/backoff/DLQ/replay; projections для device/booking context; перенос scheduler после CRON_LOCKS_MODE=shadow и on; process-kill rehearsal.

Готово: crash между commit и delivery не теряет событие; replay не дублирует эффект; старый cron выключен; DLQ и lag видны; неделя стабильной работы.

Этап 5. Web BFF

Работы: Identity/Provider internal commands вместо прямых writes; один owner account/session; BFF владеет только web-specific tables; nginx переключает web-auth, web-push, public и app-links отдельными группами; gateway удаляет внешние internal headers.

Готово: web/mobile tokens не смешиваются, admin sign-out сохраняет эффект, catalog/ETag/cookies/headers совпадают, каждая группа имеет parallel run и nginx rollback.

Этап 6. Public catalog — только по измеренной необходимости

Отдельный сервис оправдан только при доказанной read-нагрузке или самостоятельных требованиях масштабирования. Создаётся versioned read model, rebuild/checkpoint и мониторинг lag. Исходные provider/booking tables остаются собственностью Core.

Готово: source/projection сходятся, rebuild повторяем, свежесть в пределах согласованного SLA, выгода превышает эксплуатационную стоимость.

Этап 7. Пересмотр Booking/Payments/Cancellation

Это не плановый обязательный split. Он возможен только после удаления cross-domain SQL/transactions, появления Payment API, saga/reconciliation, независимых data owners и failure drills против double charge/lost booking.

Решение по умолчанию: оставить модульный монолит. Если Core удовлетворяет SLA, гибрид — конечная цель, а не промежуточная ступень к полному распилу.

4. Что остаётся в монолите

  • Booking, Payments, Cancellation и Wallet core.
  • Identity/Cognito integration и provider account.
  • Admin lifecycle с атомарными cross-table transactions.
  • Provider profile/scheduling до появления независимых read/write contracts.
  • Hair-guard orchestration: Python rendering уже отдельный сервис.
Не вводим сейчас: Kubernetes, Kafka, service mesh, отдельный Auth service и физические БД для каждого домена. Для текущей команды это увеличит сложность быстрее, чем надёжность.

5. Контрольный список проектного менеджера

  • Есть владелец результата и понятная бизнес-причина выноса.
  • Есть baseline до изменений и публичный контракт, который нельзя менять.
  • Есть тесты parity, shadow и отчёт о расхождениях.
  • Есть флаги local/remote и проверенный rollback.
  • Есть backup, миграции expand/contract и алерты.
  • Есть период стабилизации; следующий процесс не начинается раньше.
  • Contract-миграции и удаление local выполняются отдельными поздними решениями.

Hybrid transition plan — plain English

For project management · 25 November 2026 · Current code dev@75beb25f. This is a staged plan, not a production approval.

Objective: gain the benefits of selected services without visible user impact. We will not split the platform in one release. Each small extraction starts in local mode, is compared with current behavior, rolled out gradually, and can be reversed through configuration.

Target approach

Booking, payments, cancellations, profiles, and sign-in remain in a modular monolith. Separate processes are introduced only for clear operational benefits: heavy reports, background notifications, and web traffic. This avoids a distributed monolith around shared booking/payment transactions.

Rules that protect users

  • Existing URLs, response fields, statuses, errors, and v1 encryption remain compatible.
  • Local is always the default and has no dependency on the new service.
  • Shadow compares results while the monolith still serves the user.
  • Rollout starts with one entity or a small traffic cohort.
  • Database changes are additive first; old structures are removed only after stabilization.
  • Rollback uses configuration or nginx, not a new business-code deployment.

Stage 0 — Close security blockers

Disable or protect createtransfers; confirm the production PAN/CVV flag and purge; roll out Argon2id migration; close reachable SQL injection paths; replace path-segment bypass with an exact public-route registry; rotate APNs and historical secrets. Distributed entry points must not inherit open money, password, and authentication risks.

Exit: unauthorized transfer is impossible, production CVV is confirmed zero, live SQL/auth tests pass, secrets are revoked, and no critical/high dependency advisories remain.

Stage 1 — Prove operational readiness

Assign primary/backup owners, apply the sidecar migration, configure private networking, service credentials, least-privilege DB access, strict environment validation, branch protection, dashboards, and real alert routes. Rehearse backup/restore and migration rollback on the target. Record DTO/404, RPS, p95/p99, error, DB-pool, and live-v1 baselines.

Exit: the owner accepts the runbooks, alerts are tested, baselines are attached, and target rollback succeeds.

Stage 2 — Rehearse with provider-share

This read-only lookup has no payment, authorization, or external side effects. Both runtimes read the same MySQL schema, so rollback needs no data resynchronization. Start the separate image in local, enable shadow for one slug and then a small cohort, compare DTO/404/latency/errors, enable remote gradually, and repeatedly return to local through configuration.

Exit: zero unexplained mismatches, error budget met, documented rollback. Then complete 14 days at 100% remote before any contract migration or local-path removal.

Stage 3 — Move reporting workload

Move PDF/XLSX generation out of the API process to isolate CPU and memory. Use an authenticated internal API, a read-only primary DB user, PDF/XLSX and amount parity checks, email sandboxing, bounded concurrency/timeouts, and REPORT_EXECUTION=local|remote. Async jobs and replicas are separate later decisions.

Exit: matching reports and status contracts, stable Core memory, one regression-free week, proven local rollback.

Stage 4 — Move notification delivery

Every producer must write the business row and outbox event in one transaction. Use one notification writer, idempotent consumers, retry/backoff/DLQ/replay, device/booking projections, and staged cron-lock activation. Rehearse an actual process kill and recovery.

Exit: no event loss after a crash, no duplicate effect on replay, old cron disabled, visible lag/DLQ, one stable week.

Stage 5 — Introduce Web BFF

Replace direct account/session writes with Identity/Provider internal commands. The BFF owns only web-specific tables. Move web-auth, web-push, public catalog, and app-links as separate nginx route groups with independent rollback. Strip external internal headers and preserve token, cookie, ETag, and admin sign-out behavior.

Exit: web and mobile tokens remain isolated, response contracts match, every group passes parallel run and nginx rollback.

Stage 6 — Optional catalog projection

Build a separate catalog read service only when measured read traffic or independent scaling needs justify it. Use a versioned read model, rebuild checkpoints, freshness monitoring, and source/projection reconciliation. Core keeps ownership of provider and booking data.

Stage 7 — Reassess the core, do not split by default

Booking/Payments/Cancellation is not a planned mandatory extraction. It requires independent data ownership, Payment APIs, saga/reconciliation, removal of cross-domain SQL/transactions, and failure drills proving no double charge or lost booking. If Core meets the SLA, the hybrid is the final architecture, not a step toward a mandatory full split.

What we are not introducing now

Kubernetes, Kafka, a service mesh, a new Auth service, and one physical database per domain. The current team does not need that operational complexity. We will also keep booking/payment core, provider account/scheduling, admin lifecycle, and hair-guard orchestration in the existing modular system.

Project manager checklist for every stage

  • Named owner and measured business reason.
  • Baseline and immutable public compatibility contract.
  • Parity tests, shadow evidence, and mismatch report.
  • Local/remote configuration and a rehearsed rollback.
  • Backup, expand/contract migrations, dashboards, and alerts.
  • Stabilization window before another process or any contract cleanup.
