4.1. Reporting worker — первый вынос

Почему первым: узкая задача, нет записей в бизнес-таблицы, существует один публичный вход. financial-report/pdf.ts:28-31 указывает ~150 MB на Chrome; параллельность ограничена 2, очередь — 20. modules/v2/email.ts:84-129 уже проверяет provider ownership и держит per-provider in-flight guard. [высокая]

API и совместимость
  • Первый релиз: внутренний синхронный POST /internal/reports/email; существующий POST /v2/email/reports/send остаётся синхронным и возвращает те же 200/400/403/429/500.
  • Флаг REPORT_EXECUTION=local|remote обеспечивает немедленный rollback.
  • Позже отдельный новый async API: POST /v3/reports → 202 + reportId; GET /v3/reports/:id; события report.completed/failed.v1. Старый v2 не ломать.
Данные, consistency, auth
  • Сначала read-only DB user к текущей primary БД: финансовый отчёт не должен незаметно отставать. Replica — после согласованного lag.
  • Собственные таблицы не нужны для sync worker. Для async: report_jobs, metadata, S3 artifacts; не копировать payments.
  • Внешний request проходит auth в Core. Worker доступен только private network и проверяет signed service credential; providerId из внешнего headers напрямую не доверяется.

Готово: побайтовое/структурное сравнение PDF/XLSX и сумм по набору fixture periods; 429/timeout сохранены; Core не запускает Chrome при remote mode; неделя метрик без новых ошибок; rollback на local проверен. [высокая]

4.2. Notification worker — второй вынос, только после outbox

Почему не первым: producers находятся в appointment, waitlist, promo, provider-client, payments, Stripe/Twilio webhooks: текущий notifications/bootstrap.ts собирает 9 use cases, а notifications импортирует booking/payment context. Простое перемещение cron потеряет события или создаст синхронные HTTP-цепочки. [высокая]

События и API
  • Предлагаемые versioned events: booking.appointment.created/cancelled.v1, payments.outcome.changed.v1, waitlist.opening.detected.v1, provider-client.app-user-linked.v1, chat.message.received.v1.
  • Public read APIs PATCH /v2/notifications/:id/read и notification settings на первом этапе остаются в Core.
  • Worker не имеет публичного API, только health/metrics и consumer.
Данные и доставка
  • Core transaction пишет business row + outbox_events. Это устраняет dual write «БД сохранила, брокер потерял».
  • Worker владеет notification/delivery tables после перевода legacy writers. Device tokens и booking context читает через projection/API, не UPDATE.
  • Idempotency key: eventId + recipient + channel + templateVersion; retry with backoff, dead letter status, ручной replay.
  • Scheduler переносится одним флагом; старый cron в server.ts отключается до запуска нового.

Готово: тест «commit succeeds / publisher temporarily down» не теряет событие; повтор delivery не создаёт второй push; crash после отправки разрешён reconciliation/status check; все producers используют outbox; p95 задержки и DLQ видны в метриках. [высокая]

4.3. Web BFF — третий вынос

Почему кандидат: public/web routers уже монтируются отдельно до legacy middleware: server.ts:187-198. Их можно маршрутизировать nginx без изменения URL. Но ProviderWebAccountGateway напрямую вызывает legacy provider login, а web signup/reset/session пишут в общие account/device tables. [высокая]

Переносимые API
  • /v3/web-auth/*, /v3/web-push/*, /v3/public/*, root share/app-links.
  • Сначала BFF и Core работают на одной БД с одним writer per table; затем отдельная web schema.
  • Public catalog можно оставить модулем BFF, а не создавать четвёртый сервис.
Обязательная anti-corruption layer
  • Core предоставляет внутренние команды: verify customer/provider credentials, create/exchange session, reset password, revoke sessions, load provider/account snapshot.
  • BFF владеет tbl_web_session, tbl_web_password_reset, tbl_web_push_subscription; tbl_user и deviceinfo остаются Identity.
  • Admin sign-out заменяется вызовом/session event до физического разделения БД.
  • Nginx передаёт только установленные маршруты; Core не принимает spoofable account headers из интернета.

Готово: contract tests текущих web responses/cookies/headers/ETag; mobile token не проходит в web-only routes, web token не проходит в legacy routes; account writes идут только через Identity; rollback nginx на Core проверен. [высокая]

4.4. Public catalog — условный шаг, не обязательный

public-catalog/bootstrap.ts уже имеет SequelizeCatalogDatasource, но также вызывает listBookableSlots из appointment и читает provider/products/blocked dates. Поэтому сначала выделить versioned CatalogReadModel и projection; переносить процесс только при высокой доле read traffic или независимых требованиях масштабирования. API остаётся текущим 10 public routes + ETag. [средняя] Нет RPS — нет доказательства выгоды отдельного сервиса.

3. Логические schemas на том же RDScore, notifications, web, reporting; независимые migrations и credentials.Cross-schema foreign keys и transactions. Сначала backfill + dual-read/compare; dual-write только временно и через один владелец.
4. Отдельные физические БДТолько для автономных notification/web/reporting data, когда API/events закрывают все остальные чтения и записи.Перенос Booking/Payments по причине «так принято». Нужны независимый SLA, capacity и владелец эксплуатации.

Конкретные переходы данных

  • Wallet: создать wallet_accounts и полноценный ledger, backfill из tbl_user.wallet_amount/tbl_wallet_history; перевести все writers на Wallet module; dual-read compare; удалить старое поле отдельным поздним релизом. Сохранить атомарный conditional debit и history в одной transaction.
  • Web sessions: сначала убрать admin direct UPDATE и оставить один Session writer; затем backfill web tables в web schema; sign-out и password reset проверять cross-store reconciliation.
  • Notifications: перевести все producers на outbox до переноса tbl_notification; replay из outbox для backfill; сравнить количество и статусы deliveries.
  • Reporting: не копировать платёжные source-of-truth tables. Сначала read-only primary, затем replica/projection с зафиксированным dataAsOf.

8. Коммуникация, транзакции и auth

Где sync, где async

  • Sync REST внутри private network: Core → Reporting на первом этапе; BFF → Identity/Provider commands; чтение availability, если оно нужно немедленно. gRPC сейчас не нужен: существующие контракты HTTP/JSON, команда маленькая. [высокая]
  • Async outbox: notifications, projections, marketing, report completion в будущем async API. Доставка at-least-once, поэтому «exactly once» достигается только idempotent business effect, а не обещанием брокера.
  • Деньги: charge/capture/refund — синхронные команды с idempotency key; webhook и scheduled reconciliation подтверждают фактическое состояние Stripe. Не переводить денежную операцию в fire-and-forget.

Saga и reconciliation вместо распределённых ACID

Если Booking/Payments когда-либо разделяются: Booking создаёт запись в состоянии pending_payment + outbox; Payments выполняет идемпотентный checkout; событие результата обновляет Booking; timeout запускает recovery, а не автоматически удаляет запись. Cancellation использует FeeDebt и retry. Уже существующий retry-cancellation-fee.ts показывает подходящий шаблон: idempotency chain, retrieve/cancel PaymentIntent и явное requires reconciliation.

Регистрация Cognito требует аналогичной подготовки ещё в монолите: cognito.ts:369-379 вызывает AWS внутри DB transaction. Решение — состояние identity_pending, внешний вызов вне transaction, повторяемая сверка и компенсация/очистка сирот; rollback MySQL не отменяет AWS user.

Аутентификация

  • Gateway: существующий nginx только маршрутизирует и удаляет небезопасные internal headers. Не создавать новый Auth service и не переносить владение Cognito на gateway.
  • External auth: Core продолжает legacy/Cognito проверки; BFF проверяет свои web sessions. Токены и account UUID/type образуют явный principal.
  • Internal auth: подписанный короткоживущий service credential + audience + request id; user context подписывается доверенным caller. Для текущей private Docker network этого достаточно. mTLS добавлять при межхостовом трафике/compliance, а не как обязательное украшение.
  • Будущее: локальная OIDC/JWKS проверка для новых service tokens; существующий Cognito GetUser нельзя молча заменить обычным JWT cache без решения о revocation semantics.

11. Что не выносить сейчас

  • Booking + Payments + Cancellation: общие транзакции, locks, read views и циклы. Их вынос даст наибольшую цену и риск, а не самую простую победу.
  • Identity как отдельный микросервис: Cognito уже внешний generic service; локальные account/device/web/admin boundaries ещё не приведены к единому контракту.
  • Provider profile/scheduling: availability нужен Booking и catalog синхронно, а provider table содержит и account, и профиль, и Connect.
  • Admin: audit и account changes намеренно используют cross-table transactions. Это внутренний back-office, а не независимый продуктовый capability.
  • Media upload: /v2/upload/presign узкий, но S3 SDK уже делает основную работу; отдельный процесс добавит сетевой вызов без доказанной выгоды.
  • Hair-guard orchestration: rendering уже вынесен в Python. Не дробить дополнительно API session workflow.
  • Chat: сначала убрать дубли v1/v2 и определить владельца notification events; только затем обсуждать выделение.

13. Данные, которые нужны для уточнения решения

  • RPS и SLA: по route groups, особенно public catalog, slots, appointment lists, reports и webhooks; p95/p99 и допустимая недоступность. Сейчас их нет.
  • DB: размер и рост таблиц, slow queries, locks, CPU/IOPS, appointment_details profile, допустимый replica lag.
  • Production schema: read-only dump prod/pre-prod; репозиторная dev-схема не является prod baseline.
  • Legacy: живые v1 routes по 2–4 неделям журналов и минимальные версии мобильных приложений.
  • Релизы: фактическая частота production deploy и время восстановления. Число коммитов в dev не является метрикой release frequency.
  • Web: план запуска сайта и ожидаемое соотношение web/mobile traffic; это влияет на срок BFF.

[средняя] До этих данных последовательность reporting → notifications → BFF опирается на связность и изоляцию ресурсов, а не на утверждение о фактической самой высокой нагрузке.
