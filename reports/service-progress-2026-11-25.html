2. Какие проблемы действительно закрыты

  • Production schema: получен и проверен DDL без бизнес-данных; clean/prod-shaped migrations выполняются в CI.
  • Структура монолита: hub удалён; критический Booking/Payments/Cancellation/Wallet graph ацикличен; новые нарушения блокируются.
  • Консистентность: есть same-transaction outbox, durable dedup, retries, DLQ/replay, Stripe reconciliation и cron leases.
  • Runtime: compiled JS, секреты только во runtime, валидация окружения, health/readiness, graceful shutdown и безопасные 500.
  • Наблюдаемость: correlation IDs, HTTP/DB/external/runtime metrics, структурированные алерты и runbooks.
  • CI: контракты и characterization, migration tests, baseline guards, 4 API shards, aggregate gate. Main — автоматически, dev — через run-ci.
  • Обратимый вынос: отдельный image и source/compiled rollback rehearsal с нулём внешних эффектов.

3. Какая польза уже получена

  • Меньше риск релизов: регрессии обнаруживаются до merge, а не после обращения пользователей.
  • Меньше скрытого дрейфа: production схема, владельцы данных и модульные зависимости стали видимыми.
  • Меньше операционных сюрпризов: ошибки конфигурации видны при старте; процесс умеет завершаться без обрыва запросов.
  • Меньше лишней работы БД: запросы стали короче и пакетнее, без выдуманных индексов.
  • Есть безопасный путь вперёд: новый сервис можно сравнить со старым и вернуться назад конфигурацией.

4. Минусы, цена работы и оставшиеся риски

  • Денежный blocker: createtransfers по-прежнему принимает произвольные amount/account_id без проверки владельца.
  • Legacy card data: CVV теперь записывается как 0, но PAN/CVV принимаются endpoint’ом по умолчанию; production flag/purge требуется подтвердить.
  • Пароли и auth: Argon2id — capability, не завершённая миграция; public paths по-прежнему обходятся по сегментам URL.
  • SQL и секреты: generic raw conditions остаются; APNs key в git требует ротации; есть 14 moderate advisories.
  • Shared ownership: 48 legacy imports и несколько shared writers остаются; appointments/payments/notifications нельзя разделять автоматически.
  • Механизмы не равны rollout: outbox/cron locks выключены по умолчанию, outbox producer пока только payment attempts.
  • БД ещё не полностью воспроизводима: 61 legacy table не имеет tracked DDL; ProductPurchase.booking_id остаётся в модели; реальные data integrity counts не сняты.
  • Нет production proof: нет свежих RPS/p95/p99, реального shadow report, alert delivery и 14-day remote stabilization.
  • Больше операционных артефактов: появились дополнительные таблицы, флаги, workers, runbooks и образы — это полезная, но реальная сложность для команды.

5. Итоговая оценка

Работа принесла реальную пользу, а не только новые документы. Закрыты фундаментальные проблемы, которые раньше делали любой вынос опасным. Теперь есть доказанная тестами основа.

Но это не завершённый переход. Следующий шаг — закрыть security blockers и operational gates, затем выполнить provider-share rehearsal. Только после неё имеет смысл переносить reporting, notifications и Web BFF. Booking/Payments/Cancellation остаются в монолите.

Problems that are genuinely closed

  • Production DDL baseline and clean/production-shaped migration checks.
  • Service hub removal and an acyclic critical Booking/Payments/Cancellation/Wallet graph.
  • Same-transaction outbox, durable deduplication, retry/DLQ/replay, Stripe reconciliation, and cron leases.
  • Compiled runtime, runtime-only secrets, startup validation, health/readiness, safe 500 responses, and graceful shutdown.
  • Correlation IDs, runtime metrics, structured alerts, and operational runbooks.
  • Contract and characterization tests, migration CI, baseline guards, four API shards, and an aggregate CI gate.
  • Separate extraction image and source/compiled rollback rehearsal with zero external effects.

Benefits already delivered

  • Regressions are detected before merge rather than by users.
  • Schema, data ownership, and module dependencies are visible instead of implicit.
  • Configuration failures appear at startup, and requests finish during shutdown.
  • Hot SQL paths do less work without speculative indexes.
  • A new service can be compared with the current path and reversed through configuration.

Costs and remaining risks

  • createtransfers still accepts arbitrary amount/account_id without an ownership check.
  • Legacy endpoints still accept PAN/CVV by default, although stored CVV is forced to zero; production flag and purge need confirmation.
  • Argon2id is available but legacy-password migration is not complete; path-segment auth bypass remains.
  • Generic SQL conditions, APNs key rotation, and 14 moderate dependency advisories remain.
  • There are still 48 legacy imports and several shared writers; booking/payment/notification ownership cannot be split automatically.
  • Outbox and cron locks are off by default, and payment attempts are currently the only outbox producer.
  • 61 legacy tables lack tracked DDL; ProductPurchase.booking_id remains in the model; real data-integrity counts are missing.
  • There is no current production RPS/latency baseline, real shadow report, verified alert delivery, or 14-day remote stabilization.
  • New tables, flags, workers, runbooks, and images add operational complexity that the team must own.

Conclusion

The work produced real engineering benefits, not just documentation. The fundamental obstacles to a safe extraction are now addressed. The next step is to close security and operational gates, then rehearse provider-share. Reporting, notifications, and Web BFF come after that. Booking/Payments/Cancellation remains in the modular monolith.
